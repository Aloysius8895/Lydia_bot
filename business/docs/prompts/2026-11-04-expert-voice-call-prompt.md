## 2. 产品范围
第一版做“网页内语音通话”，不接电话号码、运营商或电话网关。

- 用户先选择当前项目与专家，然后点击电话入口。

- 专家角色为 steve、teresa、april、bob、ash；controller 是内部主控，不作为第六位可拨打专家。

- 通话显示对应头像、名字、通话状态、持续时间、静音、停止播放、结束、字幕开关及文字输入。

- 默认采用按住说话或点击开始/结束本轮说话的明确轮次。自动端点检测、免按键连续对话放在后续阶段，不能用假波形冒充实时理解。

- 第一版优先采用“点击开始说话 → 点击结束本轮 → 转写/可编辑 → 发送 → 等待回答 → 朗读”的半双工流程；允许后续增加按住说话，但不依赖自动 VAD 才能使用。

- 默认同一时刻只有一位专家发言。第一版不实现五专家同时发言或会议混音。

- 默认简体中文，英语可选；马来语只有在实际 STT/TTS 提供商通过测试后才能标记为已支持。混合语言、数字和专业词识别必须实测。

- 使用合成声音表达 AI 方法角色，声音不要求模仿真人。音色缺失时显示实际可用选项。

## 3. 分离语音层与专家推理层
基础链路：

`麦克风 → 本轮音频 → STT 转写 → 用户文本 → 指定专家 + 项目上下文 + 资料 → 验证后的回答 → TTS/浏览器朗读 → 播放 + 字幕`

定义可替换的能力接口，具体形式按当前 TypeScript 风格实现：

- STT：先区分浏览器直接识别与后端音频转写两种模式。浏览器模式提供 start/stop/abort 和临时/最终文字事件，不强制生成音频 Blob；本地/云端音频模式才使用 transcribe(audio, language, signal)。两者返回实际可用的文本、语言与时间信息；没有置信度就保持缺失，禁止伪造。

- ExpertDialogue：reply(caseId, role, callId, turnId, text, signal)，返回短口语回答、可显示的证据/限制和待确认事项。

- TTS：能力检查、语言/音色清单、synthesize 或客户端 speak，支持停止；明确音频由哪个设备/服务处理。

语音服务选择：

- 第一版优先检测当前浏览器 SpeechRecognition 与设备 speechSynthesis，作为不新增付费服务的候选组合。检测、真实识别和真实播放都通过后才能标记该设备支持，不能因接口存在就认定完整可用。

- 若浏览器识别不可用，检查已有本地 STT；Whisper/whisper.cpp 仅作为候选，不假设本机已安装或已有模型。不擅自下载；先列出核实过的依赖、下载大小、格式转换方式与设备要求。

- 若两种识别路径都不可用，显示“当前未配置可用的语音识别”，保留指定专家文字对话和可用朗读，语音闭环状态标为未完成。不能以文字模式可用冒充语音通话成功。

- 浏览器 SpeechRecognition 只能作为明确标注兼容性的可选适配器，不是所有设备可用的保证；不能声称原生浏览器识别一定离线。

- 浏览器识别可能由厂商服务处理音频。供应商或处理位置无法确定时记录 unknown，并向用户说明可能需要联网；“没有新增收费 API”不等于“所有数据完全在本机”。

- 本地 STT 需要实际部署、模型和音频格式转换；不要只写一个永远返回占位文本的接口。

- 浏览器 speechSynthesis 可作为初期 TTS，必须检测 getVoices/voiceschanged，按语言选择，缺少合适声音时允许文字降级。不能保证不同设备声音一致或始终离线。

- 分别记录输入与输出能力：识别可用不代表朗读可用，能朗读也不代表能识别。应用在浏览器识别模式下通常拿不到原始音频，不应伪造录音文件、编码、波形或本机转写耗时。

- 若用户选择云语音服务，独立记录服务、计费方式、数据流向和启用配置；密钥只放后端，浏览器只允许提供商支持的短时受限凭据。没有配置不得自动切换付费服务。

- 浏览器与应用后端间按轮上传可用 HTTP；采用 SSE/WebSocket/流式音频必须说明必要性，遵守同源/鉴权，并更新 CSP。流式传输不能弥补非流式 CLI 本身的生成等待。

- Provider 能力中明确 streaming STT/TTS、语言、打断、输入格式、是否传云端；不伪报能力。

第一版不要求 WebSocket/WebRTC：浏览器转写后提交文字，后端返回持久轮次 ID，前端轮询 queued/thinking/completed 等状态即可。只有确实采用本地音频转写时才增加二进制上传接口。使用 HTTP 轮询不改变 Claude CLI 的实际响应延迟，也不能据此声称全双工实时。

## 4. 指定专家与上下文
- 服务端校验角色 allowlist，不能信任前端传入任意技能路径或 prompt。

- 建立专用 dialogue 路径，复用 skills、Store、检索与证据校验模块；不要每一句都启动完整五步 research 工作流。

- “拨给 Teresa”必须真的加载 Teresa 的技能并由 Teresa 回答，不能仍通过关键字路由成 Steve/Bob；UI 与存储中的角色一致。

- 单次通话绑定固定 caseId 与角色。切换项目/专家时明确结束或建立新通话，旧回调不能写入新项目。

- 注入精简的本项目 brief、已选 Gap、用户已确认约束、本通话最近轮次与必要摘要。

- METHOD 提供方法；MARKET 才能作为市场事实证据；PROJECT 提供项目背景/约束。复用并提取已有 PROJECT 上下文能力供 dialogue 使用，不复制整个研究流水线，也不把项目介绍当作客户需求证明。

- 明确采用哪些 PROJECT 文档/片段及遗漏限制；重要约束不应仅因关键词不匹配而静默消失。

- 专家通话历史与 AI 自己的回答不是独立市场证据。对用户陈述标记 USER_REPORTED/未核实，不把这次通话计成真人客户访谈或新人口样本。

- 保留本轮实际读取的来源 ID、document/chunk/version/位置等可用信息；不让口语简化丢失范围或不确定性。

- 对重复问题可复用有效上下文/检索缓存，但项目、来源版本或约束改变后要失效。

## 5. 对话方式与结构化结果
口语回答默认先给重点，再问一个最值得澄清的问题。通常控制在一小段，以可配置字数预算约束，不机械凑字。

建议结果结构：

```json
{
  "spoken_text": "适合朗读的简短回答，保留关键限制",
  "display_text": "可带来源标注、供用户阅读的文字",
  "evidence_ids": [],
  "claim_label": "TO_VALIDATE",
  "limitations": [],
  "follow_up_question": "",
  "proposed_actions": []
}
```

- 依据当前业务需要完善 schema 和 Zod 校验。整体标签不足以表达多条主张时，应增加逐主张结构与引用检查，而不是绕开现有证据规则。

- spoken_text 与 display_text 的事实内容必须一致；朗读不可删掉重要的“仅限这几个样本”等限定。

- 没有资料时给方法建议/澄清问题，明确哪些是推断或待验证。

- 不朗读 Markdown 标记、JSON、长 URL 或每条引用编号；完整来源放字幕/详情面板。

- 语音中的“继续”“对”“就这样”不能自动选择 Gap、修改研究决策或发起完整建模。涉及状态改变时先显示候选动作，再由现有明确确认流程执行。

- 数字、金额、否定词、Gap 编号转写不确定时允许编辑和确认；不能让转写错误直接触发重要写入。

## 6. 轮次、取消与延迟
最少表达这些状态：idle、requesting_permission、listening、transcribing、queued、thinking、speaking、interrupted、ended、error。全局通话状态和每轮状态可以分开实现，避免一个布尔值管理所有异步过程。

- 每轮有独立 turnId、幂等键、顺序号和 AbortController；重复提交/重连不生成两次回答。

- 保留 CLI 并发上限。通话与研究共用调度，不通过创建第二个 CLI 实例绕过串行限制。

- 有研究任务占用推理时显示排队，可取消等待；不得为接电话擅自取消其他任务。

- 第一版“打断”至少支持停止当前朗读，并开始新的明确录音轮次。取消仅影响本通话/本轮，不能误杀其他任务。

- 半双工播放时不自动接收扬声器回声；用户主动打断后先停止 TTS，再进入监听。自动 VAD/barge-in 需另做回声与误触发测试。

- 结束、登出、切换项目、组件卸载时停止麦克风 tracks、录音器、朗读/播放、网络请求和等待队列；丢弃迟到结果。

- 区分生成了哪些文字、TTS 计划读哪些、实际确认播放了哪些；不把中断后未播放内容冒充用户已听到。提供商无法精确报告播放进度时标记 unknown。

- 刷新可恢复已保存文字，但不自动重新开麦、重播或重复扣费。

- 测量录音结束、转写完成、排队、模型返回、验证完成和首段播放时间；按配置记录延迟，不记录敏感正文到普通日志。

- 不承诺未经实测的“1 秒回复”。现有非流式 CLI 可以先做按轮可用版；若达不到用户体验目标，再评估可替换推理后端，不能偷偷换模型或付费策略。

- 需要深度研究时，专家说明可另开研究任务，由用户明确触发，不在实时回答里长时间静默跑完整链路。

## 7. 录音、格式与数据保存
- 麦克风必须由用户操作后请求权限，拒绝/无设备/设备占用时有文字入口。

- localhost 与手机 HTTPS 分开验证；手机从局域网访问须使用受信任 HTTPS，不能把电脑 localhost 当手机地址。

- 检查 MediaRecorder.isTypeSupported 或实际采样能力，记录真实 mime/codec/sample rate。WebM/Opus 不能靠改扩展名成为 WAV；STT 需要的解码、重采样应真实执行并校验。

- 根据编解码和内存限制设置单轮长度、请求大小、超时和临时文件清理；不要让现有 JSON body 处理器误接二进制音频。

- 浏览器直接识别模式默认只提交最终文字及 provider/语言等可用元数据，不额外启动 MediaRecorder 上传第二份录音。音频捕获/上传模式必须单独声明并验证；不要把两种处理路径混为一谈。

- 默认原始音频只用于本轮处理，完成/失败/取消后清理；保存录音需用户主动启用并能删除。文字记录保存策略也应明确显示。

- 在 `data/database` 新增幂等 schema 迁移/Store 接口，保持旧数据库兼容。建议有 call_sessions 与 call_turns，包含 case、role、顺序、状态、文本、错误、时间、引用 provenance、provider 与可用延迟。

- 临时音频在 business/.runtime 的受控目录；不能由静态路由公开，不放进源码、skills 或 MARKET。

- 用户可查看通话文字、修正关键转写、删除通话、导出记录。修正保留必要版本关系，不静默修改已用于决策的历史。

- 通话摘要要说明来源是系统用户与 AI 的对话。默认只做项目上下文/会话记录，不能自动升级成客户证据或人口样本。

## 8. API 和界面实现要求
- 先复用现有 API 风格设计受鉴权的创建通话、提交本轮、查询状态、取消本轮、结束通话、读取/删除记录接口。

- 服务端验证 case 与 call/turn 的对应关系；A 项目不能读写 B 项目通话。

- 普通 HTTP mutation 保留 CSRF；若用 WebSocket，做独立 Origin 与会话校验，不能仅因握手成功就信任任意消息。

- 前端入口融入现有 Conversation、专家头像、主题和移动布局。加载中显示真实 listening/queued/thinking 状态，装饰波形不能暗示识别已成功。

- 显示当前专家与项目；字幕可编辑/复制；错误可重试或转文字；键盘可操作、按钮有可访问名称。

- 本机浏览器和手机后台/锁屏、音频自动播放限制分别处理，不能承诺网页在后台保持电话能力。

可采用以下路由划分，最终命名需遵守现有后端风格；不要把尚未实现的接口列为已上线：

| 操作 | 建议接口 | 关键约束 |
| --- | --- | --- |
| 能力检查 | `GET /api/voice/capabilities` 加客户端能力检测 | 服务端不能代替浏览器检测真实音色、麦克风和识别兼容性 |
| 创建通话 | `POST /api/cases/:caseId/calls` | 角色白名单、当前案件权限、同源与 CSRF |
| 提交轮次文字 | `POST /api/calls/:callId/turns` | turnId/幂等键、文字长度、输入来源、固定 case 与 role |
| 查询轮次 | `GET /api/calls/:callId/turns/:turnId` | 只返回该通话轮次，显示实际排队/生成状态 |
| 取消轮次 | `POST /api/calls/:callId/turns/:turnId/cancel` | 仅取消本轮等待或生成，不中断其他 CLI 任务 |
| 结束通话 | `POST /api/calls/:callId/end` | 幂等、持久状态、前后端资源释放 |
| 查看/导出/删除记录 | 在既有认证 API 下设计 | 案件隔离、可追溯、删除范围明确 |

dialogue、研究任务和普通聊天必须共享原有 Claude CLI 调度。轮次入队后可返回 202，不能通过另开独立 CLI 实例制造假实时。麦克风权限与浏览器声音枚举在客户端进行，后端只报告其负责的已配置服务。

## 9. 实施顺序
1. 核实当前代码/已装语音能力/浏览器支持，写简短设计和能力表。输出“已检测到 / 待配置 / 未实测”，不推测设备已支持。

2. 实现指定专家文字 dialogue、通话/轮次存储、单案 PROJECT/MARKET/METHOD 上下文与共享 CLI 排队/取消。用 Steve 完成纵向链路，再核验其他角色。

3. 按参考图接入通话卡片、电话入口、编辑字幕、文字降级和真实状态。此时只可声明文字通话路径可用，不可声明麦克风闭环已完成。

4. 在目标电脑接入并验证一套实际可用的 STT + TTS，测一条真实语音问答；缺少配置时明确列出依赖，不假录音、假转写或假回答。

5. 完成挂断/切项目/登出清理、权限、幂等、迟到回调、角色和证据边界、播放打断测试，以及记录查看/删除/导出。

6. 使用真实设备验证中文、英语与延迟；手机 HTTPS/权限另测。之后才评估连续监听、VAD、全双工或付费实时后端。

## 10. 必须验证的场景
- 给不同专家相同问题：实际角色、技能、存储身份一致，方法侧重点可以验证。

- PROJECT 里独有的约束进入专家上下文，同时不能被当市场证据引用。

- 无证据、引用伪造、历史输出自我引用、合成数据或总体范围扩大时，不能生成假验证结论。

- 麦克风拒绝、无语言/音色、空录音、静音、格式不支持、STT 失败、TTS 失败都有明确降级。

- 用户打断/挂断、登出、切换项目、刷新后，不留麦克风占用、不播放旧回答、不重复生成。

- CLI 正在研究/排队/额度不足时，显示真实状态，不新增并发或付费后备。

- 非本人会话、CSRF 错误、伪造角色、跨项目 callId/turnId、超限音频均被拒绝。

- 中文与英文用真实音频分别验证，特别核对数字、否定词和专有名词；马来语没有实测不标通过。

- 浏览器模拟测试和假麦克风不等于真手机验收；分别报告。

- 界面验收对照 call.png，确认头像/项目/计时/三个主按钮和字幕可操作，同时验证原 27% / 42% / 31% 三栏、常展开的专家导航和 Projects 流程没有回退。

执行 business 根目录原有 `npm.cmd run check`、`npm.cmd test`、`npm.cmd run build:frontend`、`npm.cmd run test:browser`，并新增必要的语音/会话测试。真实录音、模型推理及有费用的外部服务验证按用户确认的测试范围执行，不能把 mock 标成端到端成功。

### 13.4 Lydia 专用语音验收 Skill 的建议规格

建议后续将重复验收流程整理为项目开发技能，建议名为 `lydia-voice-validation`。这是待创建的自定义技能规格，不是现成第三方插件，也不表示已安装；本次仅写入规格。若后续实施需要创建该技能，应先检查现有同类技能并复用，避免重复。

该开发技能应放在开发助手实际支持的技能目录中，并与 `business/skills/` 的专家业务技能分开。技能正文只保留流程和验收判据，较长案例、测试音频说明与报告模板按需引用，不复制整份开发 Prompt。

**触发时机：** 修改通话状态、STT/TTS 适配器、角色路由、队列/取消、记录保存，或准备声明语音通话可用时。

**固定检查流程：**

1. **核对能力与环境：** 记录实际设备、浏览器版本、输入/输出 provider、语言和处理位置，区分已检测、已实测与待配置。不因接口存在就认定可用。
2. **检查会话生命周期：** 验证开始、结束本轮、编辑、提交、排队、生成、播放、打断与挂断；另外检查登出、刷新、切项目、切专家和组件卸载。
3. **检查资源与竞态：** 确认适用模式下的 tracks、识别器、录音器、播放器、网络请求及队列已清理；用迟到回调和重复请求验证不会串案件、重复生成或恢复旧播放。浏览器直接识别没有向应用暴露 tracks 时，验证其 stop/abort 与实际收音停止，不伪造 track 信息。
4. **检查角色与上下文：** 对照实际技能加载、服务端角色、案件绑定和记录身份；检查 PROJECT、MARKET、METHOD 与 USER_REPORTED 的边界，避免 AI 历史回答成为市场证据。
5. **检查真实音频：** 在已获授权的测试范围内，用中文、英文真实输入核对数字、金额、否定词与专有名词，再验证真实专家生成和可听播放。原始音频只按原有保存策略处理，不为验收默认永久保留录音。
6. **检查降级与恢复：** 覆盖权限拒绝、无设备、空输入、无音色、provider 失败、超时、CLI 忙碌或额度不足；文字入口可用，但不能据此把语音项标为通过。
7. **检查隔离与证据：** 覆盖伪造角色、跨案件 callId/turnId、重复提交与取消范围；检查文字/朗读事实一致、引用可追溯和未知播放进度的如实标记。
8. **记录验收结果：** 用可定位的测试结果与测量支持结论；未运行、受阻和失败分开报告，不把自动化 mock 与真机实测合并成一个“通过”。

建议报告格式：

| 验收项 | 环境/输入 | 测试方式 | 实际结果 | 证据位置 | 限制或下一步 |
| --- | --- | --- | --- | --- | --- |

填写时逐项列出界面、指定专家文字对话、电脑语音闭环、手机通话及相关取消/隔离场景。该表是空白模板，不代表任何测试已执行。状态使用“通过 / 失败 / 未运行 / 受阻”，并为受阻项说明具体缺口。

### 13.5 与原实施顺序的配合

1. **代码与能力审查：** 检查现有技能、MCP、测试和依赖；有文档疑问时按需使用 Context7 或直接查官方资料。
2. **专家文字纵向链路：** 复用 Store、上下文、角色技能与共享 CLI 调度；故障时使用 systematic-debugging 的追踪流程。
3. **通话界面：** 按现有设计使用 frontend-design 的相关方法，再以现有浏览器测试或 webapp-testing 检查。确需交互探索时才补 Playwright MCP。
4. **语音与清理：** 按第 10 节及本节自定义技能规格核验真实输入/输出、取消、迟到结果和资源释放；技能尚未创建时直接执行同样的检查清单。
