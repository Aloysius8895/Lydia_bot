# 设计稿流程（pic/）

用户的规矩是：界面改动先放进 `pic/` 给他看，确认后才改正式代码和上线。下面是 2026-11-08 到 11-11 之间跑通了十几次的做法。

## 目录

1. 什么时候要出设计稿
2. 文件夹结构
3. 数据从哪来
4. 渲染脚本怎么写

## 1. 什么时候要出设计稿

**要出**：新页面或面板、改版、配色/字号/间距、新按钮或入口的位置、新交互（拖动、搜索、长按）、动画。即使用户说的是"帮我调整一下""变小一点"也算。

**不用出**，直接修好上线：
- 用户明确报告的 bug：穿模、按钮点不了、点了回不去、拖进去会变白块、内容被挤出屏幕。
- 数据、导入、运维、性能、后端逻辑。
- 用户已经看过设计稿并确认的内容。

一条消息里两类都有时就拆开：bug 直接修，涉及审美的部分出设计稿。汇报里分成"已改好"和"设计稿（还没做）"两块写。

## 2. 文件夹结构

```text
pic/<主题>-<YYYY-MM-DD>/
├─ README.md               第一行写状态："设计稿，等待用户确认"
├─ 01-xxx-light.png …      编号截图：白天/黑夜 × 电脑/手机，以及关键状态
├─ demo.webm               有动效时录一段视频（用 Chrome 打开）
├─ render.mjs              生成截图、视频和检查结果的脚本；支持 --serve 让用户自己试
├─ render-report.json      自动检查结果（PASS/FAIL）和截图说明
├─ render.log
├─ proposed\               提议的完整文件，加上对正式代码的 *.patch
└─ implemented\            上线后在真实页面截的图
```

主题名用英文短横线，例如 `magic-search-2026-11-10`、`outputs-page-2026-11-11`。同一主题改第二版时，在原文件夹里更新，README 里写"第二版"和改了什么。

做完更新 `pic/README.md` 总索引：新条目放最上面，一两句话说明是什么，加上状态（"设计稿，等待确认"/"已实现（日期）"）。

## 3. 数据从哪来

- 用**真实数据**截图。从最新的、验证通过的备份复制一份库（`data/data_storage/backups/database/**/manifest.json` 里 `verified` 和 `restore_verified` 都是 true），复制到系统临时目录或 `data/data_storage/design-copies/<主题>/`。**不要放进 `pic/`**：库里有私人数据，`pic/` 会进 git。
- 不要连正式库。服务在跑的时候，正式库也打不开。
- 缺数据时加测试数据，名字和内容标上 `TEST_ONLY`。占位卡片在界面上标"示例"，README 里写明哪些是假的。
- 如果设计需要真实的 AI 生成样本（例如简介、深入解读），可以在库副本上用真实 Claude 生成，但要在汇报里说明调用了几次。要关掉后台服务（Obsidian 同步、简介 worker），以免它们碰到真实 vault 或偷偷消耗额度。

## 4. 渲染脚本怎么写

从 `assets/design-render-template.mjs` 复制一份到 `pic/<主题>/render.mjs`，然后修改。它的做法是：

1. 从验证过的备份复制一份库到临时目录。
2. 用 `createApp({dataDir, startWorker:false, localAutoLogin:true})` 起一个真实后端，挂在随机端口上；`app.cli.run` 默认改成抛错，防止意外推理。
3. 用 Vite dev server 加一个 swap 插件：`load()` 把指定的源文件换成 `proposed/` 里的版本，`resolveId()` 让新增的文件能被引用。这样跑的是真实 React 应用，**不需要重建 `frontend/dist`**，线上不受影响。
4. 用 playwright-core 加本机 Chrome 截图。电脑用 1440×900，手机用 390×844（`isMobile:true, hasTouch:true`），白天和黑夜各一套。主题通过 `localStorage['lydia-theme']` 设置。
5. 每项检查用 `check(ok, '说明')` 记下来，最后写进 `render-report.json`。有 FAIL 时退出码为 1。
6. 动效用 `recordVideo` 录下来，存成 `demo.webm`。
7. `--serve` 模式只起服务、不截图，把地址打印给用户自己试（端口固定，例如 5310）。

设计里要接新的后端接口时，有两种做法：在 `proposed/` 里放后端模块，渲染脚本里直接 import；或者在 Vite 代理之前用一个 mock 接口挡住请求。mock 的返回格式要和真实 `api()` 一致：后端直接返回对象，不包在 `{data}` 里。

## 5. 自己先检查

截图拍完以后，**用 Read 工具逐张看**，再交给用户。常见问题：

- 文字溢出、换行难看、元素重叠（手机上尤其多）。
- 全局按钮样式把新按钮撑大或改成灰底，比如 `.knowledge-workspace button`、手机端 44px 最小宽度。
- 动画中途截图，导致测量不准。要等动画结束再测。
- 浮层或分隔线挡住了别的可点元素。测试时用 `elementFromPoint` 检查。
- 空状态、加载中、失败、没有数据这几种状态都要有截图。

发现问题直接在 `proposed/` 里修好重新渲染，并在 README 的"渲染时发现并改掉的问题"一节里写出来。

## 6. README 写什么

模板见 `assets/design-render-template.mjs` 旁边的 `assets/design-readme-template.md`。要点：

1. 标题加状态行：`设计稿，等待用户确认`。
2. 需求原话的复述，以及你是怎么理解的。
3. **先看这几张**：挑 2-3 张最关键的截图或视频，先放出来。
4. 截图表：文件名对应内容，写上实际测量值（宽度、条数、秒数）。
5. 怎么用：交互细节，包括键盘操作、Esc、双击恢复等。
6. 限制和边界：最小/最大值、手机上怎么样、什么情况下不出现。
7. 渲染时发现并改掉的问题。
8. 自动检查：N 项通过，列出检查了什么。
9. 如果确认，要改的正式文件：逐个列出，并指向 `proposed/*.patch`。确认后的动作写清楚："确认后会重建 `frontend/dist` 并重启 Lydia Remote"。
10. 需要你确认：编号问题，每个带推荐。

## 7. 用户确认后怎么实施

1. 把 `proposed/` 的改动合进正式代码。要先确认正式代码在设计之后有没有变过；变过的话，在最新版本上重新套改动，不要整文件覆盖。
2. 打补丁时，仓库开了 `core.autocrlf=true`，工作文件是 CRLF：
   - 生成 patch 用 `git diff --ignore-cr-at-eol`，否则整个文件都会被算成改动；
   - 应用用 `git apply` 或 `patch -p0 --binary`。
3. 跑相关单元测试、浏览器测试和类型检查。旧测试的断言和用户刚批准的新行为冲突时（例如聊天字号从至少 18px 改成 15–16px），改断言并在汇报里说明。
4. 按 `deploy-ops.md` 部署。
5. 在真实页面截图，放进 `implemented/`。
6. README 状态改成"已实现并上线（YYYY-MM-DD）"，写出和设计稿不同的地方。更新总索引。
7. 用完的库副本（`data/data_storage/design-copies/<主题>`）删掉，或告诉用户还留着。

用户可能只确认一部分，例如"可以就这样实现，然后字可以小点"。确认的部分实施上线；新提出的视觉改动再出一版设计稿。

## 8. 不要做的事

- 不要为了预览去 `npm run build:frontend`。线上服务启动时会列出 dist 里的文件，构建后不重启，线上页面就会坏。需要验证能不能编译时，构建到临时 outDir。
- 不要在设计阶段重启 `Lydia Remote`。
- 不要加花哨动效（见 working-agreement.md 第 3 节）。
- 不要只给静态效果图就说"做好了"。设计稿要在真实应用里跑出来，交互要能用 `--serve` 试。
- 不要把库副本放进 `pic/`。截图和视频可以用用户自己的资料，但画面里不能露出 `.env` 内容、密钥或邮箱。
