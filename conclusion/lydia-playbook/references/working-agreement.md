## 1. 用户是谁、怎么沟通

- 只有用户自己用这个 app（"这个 app 只有我自己用而已"）。用户会写代码，但主要看结果。经常在手机或 iPad 上通过 Tailscale 看线上版本。
- 用户用中文提问，夹英文词（side bar、design、output），常发截图。**回复用中文。** 2026-11-11 有一段英文进度消息冒了出来，用户问"这个是什么来的"。英文只用在代码、命令和文件名里。
- 用户的话比较短，有时有错别字（"Lyda"、"你直接" 是"你自己"）。按意思理解；有歧义时先说出你的理解，例如："你说的'聊天框'我理解成底部的分析托盘，因为能拖进去的只有它。如果你指的是别的地方，告诉我。"
- 用户常在你干活时追加需求。新需求要并进当前任务，最后的汇报逐条回应，一条都不能漏。
- 截图里有多个区域时，用户会说"截图2""截图3那页"。按编号逐一对应，回复里也用同样的编号。
- 用户问"什么意思"时，用一个具体例子解释概念。例如解释"商业模式开关"：先讲完整研究产出 Gap，再讲选 Gap 后由 Bob/April/Ash 设计谁付钱、怎么收费。
- **命令要适配用户实际的终端。** 用户有时在 cmd.exe 里运行（提示符是 `C:\...>`），这时 `Stop-Process` 不存在，要给 `taskkill /PID <进程号> /F`。PowerShell 里 npm 要写 `npm.cmd`，因为执行策略会拦 `npm.ps1`。用户显然想做某个操作但命令失败时，可以直接帮他做，比如帮他结束占用端口的旧进程。
- "怎么启动"这种问题，先查实际状态再答。用户问过三次"怎么启动"，其实服务早已通过计划任务在跑，他真正要的是那个 Tailscale 链接（"我说的是这个不是已经部署好了我是不是点这个link 就可以用了"）。

## 2. 界面：先设计、后实现

- 原话："先design 过放在pic 我验证后再决定要不要执行噢"（2026-11-08）。之后又说："你设计的记得放在pic 给我看先才执行"（2026-11-09，当时 Claude 直接改了工作台）。
- 范围：新页面、改版、配色、字号、布局、新交互、动画、新按钮的位置和样式，都先出设计稿。用户说"帮我 redesign""调整一下""变小一点"也算。
- 不算的：用户明确要修的 bug，比如"穿模了""点了回不去""拖不进去"，可以直接修好上线，修完说明改了什么。数据导入、运维、性能修复也不需要设计稿。
- 拿不准时，把能直接修的修掉，涉及审美的部分出设计稿。2026-11-09 就是这样处理的：穿模、返回、输入框变小直接上线，配色统一先进 pic。用户还在中途补了一句："这个先帮我design一下放在pic"。
- 用户确认的说法："可以""可以就这样实现""确认""都开始实现""可以执行"。没听到这类话不上线。
- 流程细节见 `design-first.md`。

## 3. 动效要克制

- 原话："那个video 我看了不用那么多effect 就书飞过来就好"（2026-11-10，看了带星光、光环、翻页的魔法书动画之后）。
- 做法：动画只做物体本身的移动，比如一段弧线，最多加一个地面阴影。不要星光、光晕、粒子、波纹、蓄力发光。加载提示（如流动的虚线外框）可以。额外的效果只作为可选方案提出。
- 侧栏拖动设计稿的写法是对的："没有动画和特效，只有那条细线淡入。"

## 4. 不乱讲

- 原话："我不要随便乱讲的"（问到项目简介是不是 Claude 真的读过 README 才写的）。
- 用户会追问 AI 生成内容的依据。要能回答：读了哪些来源、读了多少字、有没有逐句核对、抽查结果如何。不确定就如实说，例如"只有 10 个项目有 GitHub 链接，其余 97 份没读 README"。
- 生成类功能默认带原文核对，见 `ai-evidence.md` 的"原文核对模式"。
- 资料里没有的信息，界面写"来源未说明""待确认""信息有限""未独立核实"，不让模型补。

## 5. 用户做决定的方式

- 需要用户拍板时，给编号选项和推荐。能用表格对比（改动、效果、代价）就用表格。用户常只回编号，例如"改动先执行c 和d"；或逐条短答，例如"1. 保持开着吧 2. 可以 3. 什么意思"。
- 几个互斥的选择用 AskUserQuestion 问，推荐项放第一个并标 "(Recommended)"。用户通常选推荐项。
- 用户授权一个带停止条件的流程时，比如"如果预览为 5 条有效赛事、0 无效、0 冲突，现授权继续……若发现冲突或任何检查失败，停止并报告"，就严格按条件走。遇到条件没覆盖的情况（2026-11-09 是收据校验不认识 events 这个代码缺口），要么停下来问；要么在不写库的前提下修好，汇报里第一段就写"先说明一个我自己做的决定"。
- 用户问"你觉得哪个合适"，就给明确推荐和理由，不要列一堆选项让他自己挑。

## 6. 额度和费用

- 推理全部走用户的 Claude 订阅：先是 Pro，2026-11-10 用户说升级到了 Max，但 CLI 凭证还显示 pro，要用户自己 `claude auth logout` 再 `claude auth login`。没有 API key，也不要建议配 API key。
- 汇报里写"这次排查我真实调用了 Claude 大约 5 次，用掉了你订阅的一些额度"。
- 批量任务先报耗时和额度，等用户同意，例如"107 个项目大约 18 分钟，会占用订阅额度"。
- Tavily 搜索只用免费额度，有 24 小时内确认余额的门槛（见 `ai-evidence.md`）。不绕过，不接收费后备。
- `claude update` 会同时更新用户终端里的 Claude Code，要先问。

## 7. 凭据和隐私

- 原话："请勿输出凭据"。`.env` 只查有没有某个变量名，不读值（"我只看配置里的变量名，不读值"）。
- API key 让用户自己填进 `business/deployment/.env`，"不要贴到对话里"。
- 手机证书只发 `.cer` 公钥；带 `key` 的文件绝不发出去。
- CLI 的 stderr 可能带账号信息，不写进日志。`claude auth status` 只取 `loggedIn`、`subscriptionType`、`authMethod`。
- 正式库的副本含私人数据，放在被 git 忽略的 `data/data_storage/design-copies/` 或系统临时目录，**不放 `pic/`**（`pic/` 会进 git）。
- GitHub 仓库 `Aloysius8895/Lydia_bot` 是公开的。往仓库里写的任何文件（包括本 skill）都不能有邮箱、密钥、Drive 文件夹 ID、私人数据。

## 8. git 和 GitHub

- 只在用户要求时 commit 或 push。从 2026-11-04 首次推送到现在，大量改动都没提交，这是用户的选择。汇报末尾写"都还没提交到 git"。
- 工作区里有用户自己没提交的改动。不要回滚、格式化或顺手改它们。发现它们影响测试时，告诉用户由他决定。例如 2026-11-10：`knowledge-browser-test` 失败，原因是之前一处未提交的 `returnFromKnowledge` 改动。
- push 之前（2026-11-04 的做法）：
  1. 确认远端仓库状态。如果本地还不是 git 仓库，`git init -b main`。
  2. 参考 `.dockerignore` 写 `.gitignore`：排除 node_modules、`.runtime/`、`.env*`（保留 `.env.example`）、证书、`data/data_storage/`、`frontend/dist`、测试输出、抓取数据。
  3. 扫大文件和疑似密钥。第三方素材（从 Grok Bot 应用里提取的 bundle、字体、72 MB 分析 JSON）的再分发权限没确认，不推送，在 README 里说明。
  4. 确认干净 clone 也能构建：把被排除的字体临时移走，跑构建和测试。缺字体时静默退回系统字体。
  5. push 后核对远端 `main` 和本地 commit 一致。
- commit 结尾按系统要求加 Co-Authored-By 行。

## 9. 用户的数据

- 不删用户数据。365 天自动清理是用户明确要求的，规则也是用户逐条选的（见 `data-pipeline.md`）。
- 冲突时保留原数据，不覆盖、不模糊合并。
- 用户取消的任务只是从聊天里隐藏，数据库记录保留。
- 用户的研究任务停在"暂停"时，不替他取消；说明两个选项（继续/取消）让他选。

## 10. 给 Grok（每日情报台）写说明

- Grok/Didi 负责采集资料并上传 Drive。需要它改格式或重做批次时，写一段**可以直接粘贴**的中文说明，用引用块标出"（写给 Didi/Grok）"。
- 说明要具体：哪一条（id）、错在哪、怎么改、新文件夹怎么命名、ready.json 里要更新什么、以后的每日任务要遵守什么规则、做完回报什么（文件夹 ID 和条数）。
- 先在库副本上把它要交的数据试导入一遍，确认说明写对了再给。2026-11-11 的教训：上次只写了"留空"，没讲清写法，Grok 交来了 `null`，结果在 Lydia 这边做了兼容。

## 11. 犯错时怎么办

- 直接认错，说清影响，再说修复。例子：
  - "我上一条说错了。现在没有任何进程监听 `127.0.0.1`，所以电脑上打开 `http://127.0.0.1:4318` 是打不开的。"
  - "你之前说过'先放 pic 给我看，确认后再执行'，这次我还是直接改了正式代码……已经退回改动前的版本。"
- 违反了用户的规矩：先把线上恢复到之前的状态，再按规矩重做，然后把规矩写进 memory 和本 skill。
- 查不出原因就说不知道。例如服务停了但日志里没有错误时，就写"日志里没有报错，所以我不知道它为什么停了"，不要编一个原因。
